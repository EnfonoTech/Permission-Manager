Approval Matrix — Setup & Working Guide

Two approval systems on one engine. Sheet 1 routes expenses by the account they book to; Sheet 2 routes each transaction type (PO, receipt, invoice, payment…). Both are configured by data, not code. The third tab shows how to change any chain or add a new one.

What Sheet 1 configures

Excel • sheet “Service Item Purchase Order and Purchase Invoice” — columns Account | Initiate | Access | Approval 1 | Approval 2.

Every expense/service line is routed by the account the money books to. Instead of hard-coding 30-odd account numbers, each account carries an Approval Group tag, and each group owns an ordered approval chain. Any invoice or journal touching that account inherits the route automatically — so the same setup works for any company without editing code.

Golden rule for Sheet 1: tag the account, assign the people. Account → Approval Group → chain → generated workflow.

Key concepts

TermWhat it is
Approval GroupA tag on an Account (custom_approval_group, a Link field): PayrollUtilitiesOfficeRentVehicle. Decides which department head approves an expense booked there.
Position roleThe approver, e.g. Vehicle Dept Head, Finance Manager, Accountant. Roles never change per person.
Role ProfileA bundle assigned to a user that grants a position role. Change the person = reassign the profile.
Approval Group (on the invoice)A read-only header field auto-filled from the line account's group. The workflow reads this to route. Never set by hand.

Step 1 — Tag an account

The only setup step for expense routing. Open the expense/cost Account and set its Approval Group.

1
Go to Accounting › Chart of Accounts and open an expense account, e.g. Fuel Expenses – Vehicles.
2
Set the Approval Group field (e.g. Vehicle) and save.
3
Optional: tag a parent account instead — all child accounts inherit the group. Tag a few parents, not every leaf.
Tagging by account is what makes this portable: a new company just tags its own accounts — no account numbers are hard-coded anywhere.

What Sheet 2 configures

Excel • sheet 2 — columns Transaction Type | Initiated By | Approval Flow | Payment / Done | Documents Required.

Sheet 2 is per document type: each transaction (Purchase Order, Purchase Receipt, material invoice, payments, asset, employee…) has its own fixed chain, independent of the account tag. Each is a PM Workflow on that DocType. Rows that book a service/expense account (fuel, rent, utilities, petty-cash JVs) route through Sheet 1 — the two sheets meet there.

LIVE = built & running now. PLANNED = agreed in the matrix, not yet switched on (turn on the same way — see tab 3).

Purchase Order — Verbal option

A PO normally needs a Quotation attached before it can be sent. For orders placed verbally, tick Verbal (No Quotation) — a Verbal Comment box appears (and is required); write what was agreed. When Verbal is ticked, no attachment is enforced on Send for Approval.

Approving, rejecting & the guards

1
Send for Approval — the creator sends the draft; it moves to Pending and waits for the routed approver.
2
Approve — only a user holding the routed role sees Approve. Two-level routes (service PI / JV / multi-stage) go to a department head first, then the Accountant.
3
Reject — returns the document for correction; a comment is required.
Built-in guards: a user cannot approve a document they created (no self-approval); a user without the routed role never sees Approve; attachments are enforced where required (Purchase Receipt, non-verbal PO, templated JVs).

Change an approval chain (no code)

Each Sheet-1 group's chain is a record in PM Approval Group — editable in the desk. The Group Name matches the account tag; the Stages table is the ordered list of approver roles.

1
Open PM Approval Group (e.g. Vehicle).
2
Edit the Stages — reorder, add or remove approver roles (e.g. change stage 1 from Vehicle Dept Head to Operations, or insert an extra level). Per stage you can also set Require Attachment / Require Comment.
3
Save — the Purchase Invoice & Journal Entry workflows regenerate automatically from the config. No transition editing, no code.
Group tag (on the Account) → PM Approval Group (the chain) → generated workflow. Change the chain by editing data; change the person below.

Change who approves (the person)

Approvers are roles, so you never edit the workflow to change a person:

1
Open the User and set their Role Profile to the position (e.g. Vehicle Dept Head).
2
To move the role to someone else, reassign that Role Profile. Approvals in flight instantly recognise the new holder.
A person can be assigned after a document is already sent for approval — the pending item appears in their inbox as soon as they get the role.

Add a new expense category (new Sheet-1 group)

1
Create a new PM Approval Group (e.g. Marketing) and fill its Stages.
2
Save — the workflows regenerate with a branch for the new group automatically.
3
Tag the relevant Accounts with the new group (the Approval Group field is a Link, so new groups appear in the dropdown immediately).
Because the field is a Link to PM Approval Group, adding a group needs zero code — it becomes selectable on accounts and self-routes on save.

Change conditions / add a similar workflow (new DocType)

Sheet-2 flows (PO, PR, PI, JE, and the planned Payment/Asset/Expense-Claim ones) are PM Workflows generated from config. To bring a planned row online, or clone an existing flow onto another DocType:

1
Decide the chain (roles per stage) and the trigger condition — conditions read only the document's header fields (e.g. doc.custom_approval_group, doc.is_return, doc.custom_verbal, currency). They cannot read child-table rows, so any routing signal is stamped onto a header field first.
2
Add / adjust the branch in the workflow generator and run the rebuild — a one-line, idempotent operation (rebuild_approval_workflows()); running it again is safe and simply re-syncs from the current config.
3
Grant the DocType read/write to the approver roles (handled by the same rebuild) and clear cache. Test on UAT, then repeat on production.
Changing a condition (e.g. the import threshold, or which currency counts as Local) is a config edit in the same place — not a rewrite. The header-field rule is the one constraint: whatever the condition tests must exist as a header field.
Who does this: chain edits, adding a group, and changing a person are self-service in the desk. Bringing a new DocType online or changing a low-level condition is a small config change — raise it with the ERP team; it deploys UAT→production the same day.

Ad-hoc approver (Forward) — and whether it comes back

Sometimes an approval needs a one-off reviewer who isn't in the normal chain. From the inbox, an approver can Forward the item to another user. There are now two behaviours, chosen at forward time:

ModeWhat happensEnds with
Forward (hand-off)The ad-hoc reviewer takes this step. When they approve, the flow advances to the next normal stage.Ad-hoc approver is effectively final for this step; flow continues onward.
Forward & return to meTick “Return to me after their input” in the Forward dialog. The ad-hoc reviewer gives input and clicks Return — the item comes back to you to make the final call. The flow does not advance on their action.You (the originator) decide; ad-hoc is advisory only.
Choose per forward — the same document can be handed off once and returned another time. Both behaviours are always available.

Setting this up for a new company

1
Install the app (bench migrate) — it creates the Approval Group field on Account & Purchase Invoice, seeds the default groups, and activates routing.
2
Tag the company's expense accounts with their Approval Group (or tag parent accounts). No numbers, no code.
3
Create the position Role Profiles and assign users.
4
Adjust any chain in PM Approval Group to match that company's structure — the workflows rebuild from it. No per-company code.
